    Roadmap items¶

    StatisticsQ4 2026
    MinExecutions counts samples, not executions

    The flag counts scrape samples, not executions, so the threshold doesn't mean what its name says.

    Read moreShow less

    Engine.computeChangeStats compares len(preSamples) and len(postSamples) against --min-executions, so with a 60-second scrape ten samples may stand for ten executions or ten million. The flag name promises the second meaning and the code delivers the first. The fix is to separate a minimum number of samples per segment from a minimum number of executions behind each observation — which needs the per-interval execution count to be available on the sample.

    StatisticsQ4 2026
    ConfidenceScore is 1 - pValue, which is not a probability

    The score is 1 minus the p-value, which reads like a probability but isn't one. Expose the raw p-value and document the score.

    Read moreShow less

    A p-value of 0.001 does not mean a 99.9% chance the regression is real, and says nothing about the probability that a deploy caused it; the README's "0.98 confidence" example invites exactly that reading. Planned direction: expose the raw pValue (and an adjusted one, once the item below lands) on PerformanceRegression, document ConfidenceScore as a significance-derived score rather than a probability, and only later introduce a score with explicit attribution semantics. Renaming or removing the existing CRD field is a compatibility decision covered by API Versioning, not something to do in passing.

    Both kind-based workflows were validated locally but have never run on a real GitHub Actions runner.

    Read moreShow less

    .github/workflows/e2e-kind.yml and .github/workflows/e2e-kind-multicluster.yml were both authored, actionlint/YAML-checked, and validated against real clusters in a local sandbox that lacks GitHub Actions' kernel support for kind/Docker-in-Docker (see Multi-Cluster: Operational considerations for the networking workaround that local validation needed) — but neither has actually executed as a real workflow_dispatch/labeled-PR run on an actual GitHub Actions runner.     StatisticsQ1 2027
    The Welch's t-test is applied to segments chosen by the same data

    The significance test runs on a split the same data picked, so its p-value is optimistic. Calibrate it before reading it as a 5% rate.

    Read moreShow less

    Stage 1 searches every candidate split for the best E-divisive change point and stage 2 then tests that split as if it had been chosen independently, which makes the p-value optimistic (post-selection inference). The stage 0 pre-filter and the LatencyChangeThreshold mask most of the effect on typical series, but the p-value should not be read as a calibrated 5% false-positive rate. Options, roughly in order of cost: a minimum effect-size floor alongside the p-value; empirical calibration against recorded no-regression series; a permutation test that repeats the full change-point search on each permuted series. Series with autocorrelated noise are the case most worth measuring first.

    AttributionQ1 2027
    Attribution is by time proximity only, and the proximity check is symmetric

    A shift before the deploy can still be blamed on it. Make the window asymmetric, depending on how the event was timestamped.

    Read moreShow less

    evaluateQuery rejects a change point only when its absolute distance from the deploy exceeds ChangePointTolerance, so a shift that happened before the event can still be attributed to it. That is sometimes right — the ArgoCD and Argo Rollouts parsers stamp DeployEvent.Timestamp with time.Now() when the webhook arrives (typically at sync completion), while the real effect can start when the first replicas roll — and sometimes wrong. Detection Algorithm currently justifies the tolerance only by effects lagging a deploy, which is the opposite case. Planned direction: an asymmetric window whose lead and lag depend on how the event's timestamp was obtained. The OTLP source already lets an operator choose the span's start or end; the webhook sources have no equivalent, so a lightweight first step is to record a timestamp-quality indicator (source-provided vs. receipt time) on the event rather than adding separate started/completed fields to the public DeployEvent type.

    AttributionQ1 2027
    No way to say "several deploys could explain this."

    When several deploys could explain a change, say so with an Ambiguous result instead of presenting one as the cause.

    Read moreShow less

    Engine.Analyse evaluates one event at a time and every tracked query is a candidate for every event on the same watch — nothing links a queryid to an application, and pg_stat_statements does not record one. Two deploys inside one tolerance window therefore each produce their own regression for the same change point. A first step that needs no new data: when more than one event falls inside the window, mark the result Ambiguous and list the candidate events instead of presenting one as the cause. Further outcomes (Unattributed when no event is close enough, InsufficientEvidence) and candidate ranking by cluster, namespace, and workload can follow once that vocabulary exists.

    AttributionQ1 2027
    No signal for "everything got slower."

    Report how many other queries shifted at the same moment, to tell a deploy-local change from a saturated database.

    Read moreShow less

    Whether a regression is local to one query or shared by most tracked queries at the same moment is already computable from data the collector holds, and separates "this deploy changed this query" from "the database is saturated". Reporting the fraction of other tracked queries that shifted at the same change point is a cheap first control signal; richer workload context (CPU, connections, lock waits, I/O) is deliberately not planned until there is evidence the cheaper signal is not enough, since requiring it would raise the barrier to adoption.

    ValidationQ1 2027
    No real ArgoCD or pg_store_plans in the kind + CloudNativePG e2e

    The CloudNativePG e2e posts a generic webhook instead of a real ArgoCD one, and runs without pg_store_plans.

    Read moreShow less

    The kind + CloudNativePG e2e workflow (.github/workflows/e2e-kind.yml) posts a sourceType: generic webhook directly to the DeploySource route rather than standing up ArgoCD's Application controller and Notifications engine (the part that actually emits a real on-sync-succeeded webhook — see Deploy Sources & Webhooks); that's a second, mostly-orthogonal integration surface, a natural follow-up once someone needs to validate ArgoCD's own webhook delivery specifically. Separately, it doesn't run with pg_store_plans on the CloudNativePG instance: that C extension isn't compiled into CloudNativePG's default operand images, and building/maintaining a custom operand image just for this smoke test hasn't been judged worth it yet (narrower than "is pg_store_plans validated against a real server at all" — see Testing for that validation, which runs outside of CloudNativePG specifically).

    StatisticsQ2 2027
    No multiple-comparison control across queries

    Up to 500 queries are tested per pass with no correction. Options: false-discovery-rate control, or ranking by impact.

    Read moreShow less

    One Analyse or AnalysePeriodic pass can evaluate up to the top 500 queries, each against PValueThreshold, and periodic analysis repeats that on every tick. A false-discovery-rate correction (Benjamini-Hochberg is the obvious first candidate) is one option; ranking and surfacing regressions by their share of total execution time is another that also helps operators triage. Whichever is chosen, the more conservative behaviour should be a separate mode, not a silent change to what PValueThreshold means.

    Plan-diffQ2 2027
    planner.Diff compares only the root node type, total estimated cost, and snapshot source

    The diff only compares the root node, total cost and source. Walking the whole plan tree would explain the “why”.

    Read moreShow less

    A root that stays an Index Scan while its row estimate moves by four orders of magnitude, or a join order change below an unchanged root, is invisible to it. Walking the whole plan tree — scan types, index names, join methods and order, estimated rows, and sorts — would make the hint far more useful for the "why". Actual rows and buffer counts are only worth adding for sources that record them; EXPLAIN (GENERIC_PLAN) never does.

    SourcesQ2 2027
    SampleSource abstracts where samples come from, not what a sample means

    Make explicit what each observation means, so new sources can't be mixed into the same statistical test by accident.

    Read moreShow less

    internal/telemetry/promsource already requires a per-interval mean, but nothing in the interface enforces it, and a future histogram- or percentile-based source would be indistinguishable from a mean-based one to the engine. Making the meaning of each observation explicit (interval mean, cumulative mean, histogram-derived, gauge) in the sample type — with a single normalisation step in front of the engine rather than per-source conventions — would keep the engine independent of the ingestion protocol. Percentile (p95/p99) detection needs its own statistical path and calibration; feeding percentiles through the mean-based Welch test is not an option.
