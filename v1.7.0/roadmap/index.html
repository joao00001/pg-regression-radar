    Roadmap¶

    What's still open — planned features, known gaps, and operational follow-ups. What's already shipped lives in CHANGELOG.md and in each feature's own docs page, not repeated here.

    Overview¶

    This page tracks only what's not done yet: planned features, known robustness gaps, and operational follow-ups that aren't code changes. It is not a running history of delivered work — once an item here ships, it's removed from this page, not reworded as "done"; its details live in CHANGELOG.md (what shipped and when) and the relevant feature's own docs page (how it works today).

    Feature roadmap¶

    This project does not commit features to specific version numbers — a version tag marks when something shipped, not a promise of what a future one will contain. What's below has no version committed yet:

    • GitHub/GitLab PR comment on detected regression; Grafana annotation.
    • An OLM bundle for OperatorHub.io.
    • OpenTelemetry as an alternative, opt-in input to the Correlation Engine (Prometheus-backed SampleSource first) — see below for the phased plan and why this is additive, not a replacement for internal/collector.Collector.

    OpenTelemetry as a pluggable analysis input, in detail¶

    The OpenTelemetry Collector's postgresqlreceiver (opentelemetry-collector-contrib) now scrapes pg_stat_statements natively — per-query latency, call counts, and cache stats, exposed as a postgresql.query.execution.time metric plus a db.server.top_query log record. That means the "scrape pg_stat_statements and expose per-query stats" half of this project is being commoditized by the wider ecosystem. Nothing in OTel's core semantic conventions or collector-contrib, however, does deploy-correlated change-point detection (see Detection Algorithm) or EXPLAIN plan-diff capture (see Detection Algorithm: Plan-diff correlation) — that pairing is this project's actual differentiated value, not the collection step.

    This is a low-risk pivot because the seam already exists and requires no changes to either: correlation.Engine depends only on a two-method SampleSource interface (SamplesInRange, AllQueryIDs — internal/correlation/engine.go), not on internal/collector.Collector concretely, and deploy events reach Engine.Analyse as a plain v1alpha1.DeployEvent value regardless of which webhook DeploySource produced it (see Deploy Sources & Webhooks). A new input just has to satisfy the same interfaces.

    Phased plan:

    1. Prometheus-backed SampleSource (additive, opt-in) — shipped, including wiring. internal/telemetry/promsource implements correlation.SampleSource via PromQL range queries against whatever a fleet's OTel Collector prometheusexporter is already serving — see OpenTelemetry / Prometheus Sample Source for a real caveat found while building it: postgresqlreceiver's stock postgresql.query.execution.time metric has no per-query attribution as of this writing (it's scoped to db.namespace only), so this source requires a custom recording rule or OTel pipeline to supply a per-queryid metric, rather than working out of the box against a bare OTel Collector install. It's plugged in as an alternative to internal/collector.Collector at the same injection point (internal/controller/postgreswatch_controller.go's startWatch), selected declaratively via spec.sampleSource.type: prometheus on PostgresWatch — see OpenTelemetry / Prometheus Sample Source § Using it from a PostgresWatch CRD. dsn/dsnSecretRef aren't required in that mode, and capturePlans: true is rejected at reconcile time when combined with it (no direct database connection to EXPLAIN against). Default behavior is unchanged either way — internal/collector.Collector's direct pg_stat_statements scraping remains the zero-extra-infrastructure default and is never removed; this is for fleets that already run an OTel Collector and would rather not run a second scraper against the same database. Still open: a full worked example otel-collector.yaml (the receiver → exporter → recording-rule pipeline end to end) — that's Phase 1c.
    2. OTel-sourced deploy events (lower priority). Normalize an OTel span (e.g. an ArgoCD sync span) into a v1alpha1.DeployEvent through the same EventStore.Add path existing webhook DeploySources already use. Deferred behind step 1 gaining real usage, since ArgoCD/Flux/GitHub/generic webhooks already cover this directly today.
    3. Export PerformanceRegression as an OTLP-compatible signal. Once a regression is detected — regardless of which SampleSource fed it — emit it as an OTLP log record or span event too, so any OTel-native backend (Grafana, Datadog, etc.) can consume a detected regression without this project's own dashboard API. Complementary to, not a replacement for, existing Slack alerting.

    Deliberately staying out of scope for all of the above: EXPLAIN/plan-diff capture. No OTel component or semantic convention captures execution plans as of this writing — that stays internal/planner's own logic regardless of which SampleSource is active.

    Known robustness gaps¶

    • Real auto_explain log ingestion is not yet built. internal/planner captures a query's execution plan from either pg_store_plans (the real, previously-executed plan — see Testing for how it's validated against a real install) or EXPLAIN (FORMAT JSON, GENERIC_PLAN) (an estimate, PostgreSQL 16+ only) and diffs two captures — see Detection Algorithm. A full auto_explain log-shipping pipeline remains a heavier, not-yet-started alternative for clusters that have neither pg_store_plans nor PostgreSQL 16 available — see the "Honest limitations" note on Detection Algorithm.
    • No real ArgoCD or pg_store_plans in the kind + CloudNativePG e2e. The kind + CloudNativePG e2e workflow (.github/workflows/e2e-kind.yml) posts a sourceType: generic webhook directly to the DeploySource route rather than standing up ArgoCD's Application controller and Notifications engine (the part that actually emits a real on-sync-succeeded webhook — see Deploy Sources & Webhooks); that's a second, mostly-orthogonal integration surface, a natural follow-up once someone needs to validate ArgoCD's own webhook delivery specifically. Separately, it doesn't run with pg_store_plans on the CloudNativePG instance: that C extension isn't compiled into CloudNativePG's default operand images, and building/maintaining a custom operand image just for this smoke test hasn't been judged worth it yet (narrower than "is pg_store_plans validated against a real server at all" — see Testing for that validation, which runs outside of CloudNativePG specifically).
    • Neither kind-based e2e workflow has a real GitHub Actions run yet. .github/workflows/e2e-kind.yml and .github/workflows/e2e-kind-multicluster.yml were both authored, actionlint/YAML-checked, and validated against real clusters in a local sandbox that lacks GitHub Actions' kernel support for kind/Docker-in-Docker (see Multi-Cluster: Operational considerations for the networking workaround that local validation needed) — but neither has actually executed as a real workflow_dispatch/labeled-PR run on an actual GitHub Actions runner. Treat each workflow's first real run as part of reviewing the change that introduces it, not as an already-passing check.

    Operational follow-ups¶

    Shipped operational work (publishing signed release artifacts, per-release docs versioning, per-PR release-notes fragments) is documented where it actually lives — CI/CD and Installation — and logged in CHANGELOG.md, rather than listed again here once it's done. What's below is genuinely still open:

    • Branch protection review. See Branch Protection — the CI checks in CI/CD only have real effect once main's ruleset actually requires each one by name.
    • GitHub Discussions link. .github/ISSUE_TEMPLATE/config.yml links to the repo's Discussions tab; whether Discussions is actually enabled on the repo hasn't been confirmed.

    7-step security and robustness checklist status¶

    This repository's code/docs/workflow-addressable checklist has 6 of its 7 steps complete — security model and trust boundaries, secret-consent and policy controls, alert destination controls, Kubernetes hardening defaults, the tenant-safe remote cluster model, and supply-chain controls, in that order. Each is documented in full on its own page, not restated here: Security Model, Multi-Cluster (Fleet) Mode, Deployment Security, and Supply Chain cover how; CHANGELOG.md covers when.

    Step 7 remains intentionally operational, and genuinely open:

    • External-user quickstart validation is reproducibly documented but not auto-provable from code alone. The execution checklist exists in Quickstart Validation, but completion still depends on a real human/operator run in an external environment.
