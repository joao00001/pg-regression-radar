# v1.0 release notes — working draft

*Status: draft, for the project owner to decide exact scope/version number
against. Not published anywhere, not linked from the docs site nav or
`mkdocs.yml`. Delete or move into `docs/` proper once the scope decision in
this document is made and a version number is picked (this document
deliberately doesn't assume it'll be called "v1.0" — see the note in
[`docs/roadmap.md`](../roadmap.md#version-roadmap): that name is likely but
not yet decided).*

This covers every commit merged to `main` between `v0.1.0` and now (47
commits — see [`CHANGELOG.md`](../../CHANGELOG.md) for the full, categorized
list with commit links), plus two branches not yet merged that this
document treats as in-scope prerequisites, not optional extras — a release
can't be tagged/published without the first, and the second only exists to
generate this kind of document automatically going forward:

1. `ci/release-publishing` — adds `.github/workflows/release.yml` itself
   (GHCR image + Helm OCI publishing, Trivy scanning, SBOM, cosign
   signing). Without this merging first, there is no way to actually cut
   and publish *any* tagged release, v1.0 or otherwise.
2. `feat/release-notes-automation` (this branch) — adds the `release-notes`
   job to that same workflow, `cliff.toml`, `CHANGELOG.md`, and this
   document. Stacked on top of (1); must merge after it, in that order.

If the project owner decides either of those two branches needs more work
before merging, that pushes the earliest possible release date out
accordingly — everything below assumes both land as currently written.

## What this release delivers

**Detection & correlation improvements:**

- Regression findings are now deduplicated across a `queryid` rotation.
  Previously, a query whose `queryid` changed mid-analysis-window (a normal
  PostgreSQL behavior on planner-relevant schema changes) could be reported
  as two separate regressions instead of one continuing one.
- Plan-diff correlation: the correlation engine can now capture and diff a
  query's execution plan around a detected regression, from either of two
  sources — `EXPLAIN (FORMAT JSON, GENERIC_PLAN)` (PostgreSQL 16+, an
  estimate) or, when available, `pg_store_plans` (the real, previously
  executed plan — preferred when present). **Important caveat**, spelled
  out fully in the gaps section below: this capture/diff logic exists and
  is unit-tested, but is not yet wired into the alert path, so no
  `PerformanceRegression` a user actually receives carries a plan diff yet.
- `cmd/manager` now backfills its in-memory detection state from the
  Postgres persistence backend on restart, instead of starting cold.

**Multi-cluster (fleet) support:**

- A `PostgresWatch` can now point at a Postgres cluster running in a
  *different* Kubernetes cluster than the manager itself
  (`spec.remoteClusterSecretRef`, a kubeconfig Secret in the hub cluster).
  Previously this required manually copying the DSN Secret between
  clusters by hand. Several real gaps remain here — see below; this is a
  first pass, not a finished fleet story.

**Security:**

- The ingester's webhook endpoint now requires an `X-Webhook-Token` bearer
  token. Previously any network path that could reach the ingester could
  post a fabricated deploy-event webhook with no authentication check at
  all.

**Performance:**

- Six separate performance changes reduce algorithmic complexity or
  allocation pressure across the collector, ingester, and correlation
  engine's hot paths (E-Divisive O(n³)→O(n²), several O(N)/O(N×M) poll and
  scan loops replaced with cursor-based or O(1) equivalents, reduced lock
  contention in `Engine.Analyse`, and slice pre-allocation to cut GC
  pressure). None of these change behavior — they're the same detection
  logic running measurably faster/lighter under load.

**CLI & developer experience:**

- A single unified `pg-regression-radar` CLI binary now wraps all
  subcommands, so `go install` sets up everything from one target instead
  of four.
- `--version` and `--dry-run` flags were added across all four binaries.

**CI/CD & quality (once `ci/release-publishing` is merged too):**

- A real `kind` + CloudNativePG e2e workflow validates `cmd/manager`'s CRD
  mode against an actual Kubernetes cluster and Postgres operator
  (`e2e-kind.yml`) — not yet proven green in a real run; see gaps below.
- A documented, CI-enforced PostgreSQL 16/17/18 + EDB Postgres Advanced/
  Extended Server support matrix.
- Expanded e2e coverage against a real PostgreSQL instance for the features
  above.
- (From `ci/release-publishing`, assumed merged first) Tagged releases
  publish five container images and a Helm chart to GHCR, Trivy-scanned,
  SBOM-attested, and cosign-signed.
- (From this branch) Every tagged release gets auto-generated, categorized
  release notes as a real GitHub Release, and the full history back to
  `v0.1.0` is captured in `CHANGELOG.md`.

**Documentation:** a full MkDocs Material documentation site was stood up
(previously just a `README.md`), covering architecture, the detection
algorithm, configuration, installation, multi-cluster mode, the support
matrix, API/CRD versioning policy, and this roadmap — see
[`docs/index.md`](../index.md).

## What's left out / known gaps

This section is deliberately exhaustive and unflattering — it's the input
for deciding whether to ship this as "v1.0 with documented gaps" or hold
for more work first. Pulled from [`docs/roadmap.md`](../roadmap.md) plus
this branch's own not-yet-proven pieces; nothing here is invented, and
nothing known was left out.

### Never validated against real infrastructure

- **`pg_store_plans` has never been tested against a real PostgreSQL
  server with the extension actually installed.** It's a third-party C
  extension this project's sandboxed CI/dev environments can't install;
  the code path is only exercised against a fake `*sql.DB` in unit tests.
- **`e2e-kind.yml` (real `kind` + CloudNativePG cluster) has never
  actually run.** The sandbox it was authored in has no Docker-in-Docker/
  `kind` support. Commands were checked against current upstream docs and
  the YAML is syntax/`actionlint`-clean, but the first real
  `workflow_dispatch` run is still outstanding.
- **`release.yml` (GHCR image + Helm publish, Trivy, SBOM, cosign) has
  never pushed to a real registry.** No Docker daemon was available in the
  environment it was authored in — not even a local `docker build` of the
  five image targets was exercised, let alone a real push, a real cosign/
  Fulcio OIDC exchange, or a real Helm OCI push.
- **This branch's `release-notes` job has never run in a real Actions
  environment either**, for the same reason. What *was* validated for
  real: `git-cliff` itself was downloaded as a prebuilt binary (matched to
  this sandbox's `aarch64` architecture) and run directly against this
  repository's actual `git log` history; its output was diffed
  commit-by-commit against `git log v0.1.0..main` to confirm all 47
  commits are accounted for with none lost or invented (see
  `CHANGELOG.md`'s own header). The `orhun/git-cliff-action` wrapper and
  the `softprops/action-gh-release` call around it are unproven the same
  way the rest of `release.yml` is.
- **Multi-cluster (fleet) mode has never been validated against two real
  Kubernetes clusters.** Tests use `sigs.k8s.io/controller-runtime/pkg/
  client/fake` plus a syntactically valid kubeconfig pointing at an
  unreachable address — not an actual second `kind` cluster.
- **Real ArgoCD was never stood up for the e2e workflow.** It posts a
  `sourceType: generic` webhook directly rather than exercising ArgoCD's
  own Notifications engine and webhook delivery.

### Implemented but not fully wired up or finished

- **Plan-diff correlation isn't in the alert path yet.** Nothing in
  `internal/correlation` or `internal/alerting` calls
  `planner.CapturePlan()` — the capture/diff logic exists and is tested in
  isolation, but a `PerformanceRegression` a user actually receives today
  carries no plan diff.
- **Multi-cluster mode has no kubeconfig rotation/expiration handling.**
  An expired token just starts failing DSN resolution
  (`status.phase: Failed`) with no automatic refresh.
- **The remote client cache never evicts entries.** Fine at the fleet
  sizes this project targets; not fine at very large scale.
- **No remote-namespace override.** The DSN Secret must live in a
  same-named namespace on the remote cluster as on the hub.
- **The CloudNativePG `Cluster` resource itself is never read remotely** —
  only the generated DSN Secret. `clusterName` stays a free-text label.
- **No multi-architecture images.** Every image builds for the runner's
  native platform (`linux/amd64`) only.
- **Helm chart signing not implemented.** The five container images are
  cosign-signed; the Helm OCI artifact is not.
- **`Chart.yaml`'s checked-in `version`/`appVersion` drift from reality.**
  `helm package --version --app-version` overrides both at publish time
  from the git tag, so the checked-in values are a development-time
  placeholder, not the last-published release.
- **GHCR publishing needs a one-time manual repo setting** (Settings →
  Actions → General → Workflow permissions → "Read and write
  permissions") that can't be set from workflow YAML — the very first tag
  push will 403 until this is done once.

### Not started at all

- **OLM bundle for OperatorHub.io.** Listed in the version roadmap as part
  of "v1.0 (in progress)"; no code or packaging work has begun.
- **GitHub/GitLab PR comment on detected regression; Grafana annotation.**
  Scoped for a later "v0.4"-labeled milestone in the roadmap, not this
  pass.
- **Real `auto_explain` log ingestion** as a heavier alternative to
  `pg_store_plans` for real (not estimated) execution plans — explicitly
  out of scope for both plan-diff sources shipped so far.
- **`pg_store_plans` on the CloudNativePG e2e instance.** It isn't
  compiled into CloudNativePG's default operand images; building a custom
  operand image for this wasn't judged worth it yet.

### Process / housekeeping gaps, not code

- **Branch protection review.** The CI checks documented in `docs/ci-cd.md`
  only have real effect once `main`'s ruleset actually requires each one
  by name — not confirmed done.
- **GitHub Discussions link unconfirmed.** `.github/ISSUE_TEMPLATE/
  config.yml` links to the repo's Discussions tab; whether Discussions is
  actually enabled hasn't been checked.
- **A stale doc was found and fixed while researching this release**
  (worth flagging so it isn't mistaken for a code change): `docs/
  roadmap.md` still listed "no dedup of findings across a queryid
  rotation" as an open gap, but that was fixed by commit `4c62488` back in
  the history covered by this release. The stale line was removed as part
  of this branch, since `docs/collector-internals.md` already correctly
  described the fix.

## Recommendation for the scope call

Everything in "What this release delivers" is real, working code with unit
test coverage. The common thread across nearly every gap above is the same
one: **written and reviewed, but never exercised against real external
infrastructure** (a real Postgres with `pg_store_plans`, a real second
Kubernetes cluster, a real `kind` cluster, a real GHCR push, a real GitHub
Actions tag-push run). That's a materially different — and more
bounded — kind of gap than "not implemented," and worth weighing on its
own terms when deciding whether "v1.0 with these gaps documented" is
honest enough to ship, or whether one or more of the "never validated"
items should get a real end-to-end run first.
