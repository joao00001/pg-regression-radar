Remote clusters can now be pre-registered by administrators using the new `PostgresRadarCluster` CRD (cluster-scoped), and `PostgresWatch` resources reference them by name via `spec.remoteClusterRef` instead of pointing directly at arbitrary kubeconfig Secrets.

**New: `PostgresRadarCluster` CRD**

```yaml
apiVersion: radar.pgregressionradar.io/v1alpha1
kind: PostgresRadarCluster
metadata:
  name: prod-eu-west
spec:
  kubeconfigSecretRef:
    namespace: pg-radar-system
    name: prod-eu-west-kubeconfig
    key: kubeconfig
  namespace: postgres   # optional default remote namespace
```

**Updated: `PostgresWatch.spec.remoteClusterRef`**

```yaml
spec:
  remoteClusterRef: prod-eu-west   # name of a PostgresRadarCluster
  dsnSecretRef:
    name: prod-eu-west-app-superuser
    key: uri
```

This eliminates the confused-deputy risk where any watch creator could reference an arbitrary kubeconfig Secret. With `remoteClusterRef`, only administrators (who have create/update access to `PostgresRadarCluster`) decide which remote clusters are reachable.

**Security profiles**

The manager and operator support a `--security-profile` flag with two values:

- `controlled` (default): both `remoteClusterRef` and the now-deprecated `remoteClusterSecretRef` are accepted. A deprecation warning is logged whenever the old field is used.
- `hardened`: `remoteClusterSecretRef` is rejected outright; only the registry path (`remoteClusterRef`) is allowed.

See [docs/multi-cluster.md](docs/multi-cluster.md) for the migration guide from `remoteClusterSecretRef` to `remoteClusterRef`.
