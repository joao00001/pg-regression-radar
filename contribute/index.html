    Build it with us¶

    pg-regression-radar is open source and small enough to read in an afternoon. Break it on your own Postgres, fix a typo, review a pull request or take on a real issue. All of it counts, and you don't need anyone's permission to start.

    Your first pull request¶

    01
    Fork and clone
    Fork the repository on GitHub, then clone your copy.
    git clone https://github.com/<you>/pg-regression-radar
cd pg-regression-radar
    02
    Check it builds
    The unit tests need no database or cluster.
    go build ./... && go vet ./... && go test ./...
    03
    Branch and commit
    Conventional Commits, signed off with -s.
    git switch -c fix/short-description
git commit -s -m "fix(collector): short summary"
    04
    Open the pull request
    Push the branch and open the PR. CI checks the title, the sign-off, formatting and tests, and a maintainer takes it from there.
    git push -u origin fix/short-description

    A small fix? Just open the pull request. Something bigger? Open an issue first so we agree on the approach before you write it. The full guide covers branch names, tests, docs and release notes, and our testing and CI/CD pages show what runs on your PR.

    What to expect¶

    Talk first for big changes
    Typos and bounded fixes can go straight to a pull request. Anything larger starts as an issue, which saves you from writing code that needs a different design.
    CI does the checking
    Formatting, vet, tests, sign-off and the PR title run on every pull request. From a fork, a maintainer may need to approve the first run and add a label for the slower integration suites.
    Messy commits are fine
    Pull requests are squash-merged, so only the PR title ends up in history. Commit as often as you like while you iterate.
